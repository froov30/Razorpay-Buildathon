## 2. Project context

### The problem

Marketplace and platform settlements involve more than "payment amount minus platform
fee." A single order's money must be split across a seller, a delivery partner, the
platform, and sometimes a promotion budget — and how it splits depends on the seller's
contract, whether delivery was confirmed, whether the order was returned or refunded,
and which version of the agreement was active at the time.

A payment record can prove money was collected. It cannot prove a seller was actually
*entitled* to receive their share at the moment a transfer went out — e.g. paid before
delivery was confirmed, paid under an outdated commission rate, or a refund issued
without the matching seller payout being reversed first.

**The gap:** nobody is verifying economic entitlement against the contract — only
verifying that the ledger is internally consistent.

### Target audience

Marketplace/platform CFOs and finance controllers, seller-operations and settlement
teams, delivery/gig platforms with partner payout obligations, and franchise/multi-vendor
e-commerce operators.

### The solution, in one sentence

It doesn't just check that the money that moved matches the books — it checks that the
money that moved matches what the contract actually promised.

### Critical differentiation — state explicitly and prominently

Razorpay already ships an AI-powered, production-scale reconciliation product
(Optimizer / Single View Recon) that matches settlements against bank statements and
gateway records. EntitleGraph is **not** a reconciliation clone. This line must appear
verbatim in `README.md`, `docs/architecture.md`, and `DEMO.md`:

> **"Razorpay Recon proves the money that moved matches the settlement records.
> EntitleGraph proves the money that moved matches what the contract actually promised."**

Recon asks *"does the ledger agree with itself?"* EntitleGraph asks *"was this party
contractually entitled to what they received?"* — a semantic, contract-interpretation
question Recon does not ask. Put it in the first screen of the README and the first
15 seconds of the demo script.

### Hard constraints (non-negotiable)

- **No real money movement.** All Razorpay API calls run in test mode only. Keys come
  from environment variables; never hardcode credentials.
- **No proprietary or scraped real merchant data.** All data is synthetic, generated by
  this project, and labeled as such in code, docs, and UI.
- **No production integrations.** This is a reference implementation and every doc must
  say so plainly.
- **Confidence-tiered output.** Every entitlement decision carries a tier
  (`auto_clear` / `needs_review` / `blocked`) — never a bare true/false.
- **Honest exception list.** The system must be able to say "I don't know, here's why"
  for genuinely ambiguous cases. Do not force every record into a clean auto-cleared
  bucket — that reads as fabricated to a technical judge.

### Tech stack

Python 3.11+, FastAPI (API layer), Streamlit (dashboard), SQLite (event store). No
heavyweight infra — no Kafka, no Postgres server, no Docker cluster. Must run with a
single setup command on a judge's laptop.

### Buildathon submission requirements (confirmed)

Submission must include: (1) a public GitHub repository, (2) a 5-minute pitch video,
(3) an architecture diagram, and (4) an explicit explanation of what broke during
development and how you recovered. Track 4's judging bar is throughput across a batch
of synthetic records, measured accuracy, and an honest exception list.

You produce everything for (1), (3), and (4) plus a demo script. You cannot record
video — leave a clearly marked placeholder in `DEMO.md`.

### The required "what broke" narrative

Deliberately build and document one genuine failure scenario: a **contract-version
conflict** — a seller's commission rate changes from 70% to 65% mid-month with an
ambiguous effective date, such that the system cannot cleanly determine which rate
applied to orders in the boundary window. Build it into the synthetic data on purpose,
show the system correctly refusing to auto-resolve it (routing to human review instead
of guessing), and document the debugging journey honestly in `docs/CHANGELOG.md`.

### Evaluation metrics — implement and surface all of these

| Metric | Definition |
|---|---|
| Exact entitlement-match rate | % of records where computed entitlement matches actual settlement exactly |
| Exception precision / recall | Against ground-truth exception tags injected into synthetic data |
| Amount-weighted accuracy | Accuracy weighted by transaction value, not record count |
| Auto-close rate | % of records resolved without human review |
| Throughput | Records processed per second |
| Unsafe-action count | Must be **provably zero** — no transfer or reversal fires without passing the entitlement gate |
| **`[v2]` Prevented loss (₹)** | **Rupee value of incorrect payouts caught before firing — the headline stat** |

## 3. `[v2]` Revised scope and sequencing

The original prompt specified seven parallel phases. That is a team-sized sprint and
produces shallow modules. **Depth beats breadth for a technical judge.** Revised rule:

> **Build one contract type end-to-end until it is airtight, then widen.**

The vertical slice — compile → entitlement → gate → blocked/approved transfer → audit
log — must be fully working before any second contract type, before the dashboard, and
before data variety is expanded. A good-looking demo over a hollow engine is the
fastest way to fail a judge's follow-up questions.

**Priority order when time is short** (cut from the bottom, never the top):

1. Contract Compiler + Policy DSL (the differentiator)
2. Settlement engine with integer-paise arithmetic
3. Entitlement gate + audit log + adversarial gate test
4. Synthetic data incl. the version-conflict case
5. Evaluation harness and metrics
6. Dashboard
7. API surface
8. Breadth of contract types and exception categories

## 5. `[v2]` Engineering requirements baked into this revision

### 5.1 Contract Compiler is the centerpiece — treat it that way

The entire pitch rests on "we interpret contract semantics, Recon doesn't." The
compiler gets disproportionate depth. It must demonstrate at minimum **four genuinely
hard clause situations**, each with a written explanation of how the DSL resolves or
refuses it:

1. **Mid-cycle rate change with ambiguous effective date** (the required failure case)
2. **Overlapping promotions** where funding responsibility is split and two clauses
   both claim the same discount
3. **Delivery-contingent holds** where entitlement depends on an event that may never
   arrive
4. **Refund precedence** — whether commission is refundable, and whether seller payout
   reversal must precede customer refund

A judge will probe this module hardest. Shallow extraction here sinks the submission.

### 5.2 Compile once, cache canonically — determinism is graded

The compiler is LLM-backed, but the evaluation metrics must be reproducible on judging
day regardless of API availability or model drift. Therefore:

- Compile each contract **once**; persist the resulting Policy DSL as canonical JSON in
  `data/synthetic/compiled_policies/`, keyed by a content hash of the source text.
- The settlement engine reads **only** the cached artifact and is fully deterministic.
- A cache hit never calls the LLM. `--recompile` forces a refresh.
- If no LLM key is present, a clearly-labeled deterministic parser backend produces the
  same DSL shape so the pipeline never blocks.
- Document this as a deliberate design decision in `docs/TRD.md`.

### 5.3 LIVE vs MOCK must be loud, never silent

Silently falling back to mock when keys are absent undercuts credibility with a
Razorpay judge. The client exposes an explicit mode that is surfaced in logs, the API
response envelope, and a dashboard banner:

- `LIVE-TEST` — real Razorpay test-mode API calls (Linked Accounts, transfers, reversals)
- `MOCK` — local simulation, banner reads "MOCK MODE — no Razorpay API calls made"

The recorded demo should run in `LIVE-TEST`.

### 5.4 Prevented loss (₹) is the headline metric

Amount-weighted accuracy is a technical metric; **"₹X in incorrect payouts caught
before they fired"** is what a non-technical judge remembers. Compute it as the sum of
the variance on every proposal the gate blocked, and render it as the largest number on
the dashboard.

### 5.5 Prove the gate, don't just observe it

`unsafe_action_count == 0` from a clean run is weak evidence. Ship an **adversarial
test** that deliberately attempts to fire a transfer around the gate — direct client
call bypassing the check, replayed approval token, mutated entitlement after approval —
and asserts each attempt is refused and audit-logged. A gate that has never been
attacked has not been tested.

## 7. Build sequence

**Phase 1 — Foundations.** Scaffold structure. `.env.example` with
`RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `ANTHROPIC_API_KEY`. Money primitives
(integer paise, no floats anywhere). Razorpay client with explicit LIVE-TEST/MOCK modes.

**Phase 2 — Contract Compiler (centerpiece).** Policy DSL schema, versioned per
contract. LLM extraction backend + deterministic fallback backend. Canonical compile
cache. The four hard clause situations from §5.1, with tests.

**Phase 3 — Vertical slice.** One contract type end-to-end: entitlement graph event
model, deterministic settlement computation, matcher against actual transfers, gate,
audit log. Do not proceed until this is airtight.

**Phase 4 — Synthetic data.** ~90–120 linked lifecycle records: ~10 contracts (incl.
the 70%→65% version conflict), 40 orders, 40 payment events, 40 transfers, 30 delivery
events, 15 promotions, 15 refunds/reversals, ~20 records tagged as exceptions across
premature payout, missing reversal, duplicate transfer, tax-line mismatch, version
conflict, and at least one genuinely ambiguous case. Ground-truth labels stored
separately from what the system sees.

**Phase 5 — Exceptions and gating at full breadth.** Rule-based root-cause
classification with LLM-generated plain-language explanations. Maker-checker approval
in front of every Route call. Adversarial gate test (§5.5). Confirm the version-conflict
case routes to human review rather than guessing.

**Phase 6 — Evaluation.** Unit tests per module, full-batch integration test, and
`tests/eval/` computing all seven metrics against ground truth with a clean printed report.

**Phase 7 — Dashboard.** Fund-flow view, blocked-payout view, exception review queue,
live metrics panel with prevented-loss as the headline. Make blocked-then-approved
visually obvious — that moment should do the pitch's work on its own.

**Phase 8 — Documentation close-out.** Finish docs against what was actually built,
diagram from real final component boundaries, README last, `DEMO.md` as a 5-minute
script: hook (10–15s) → Recon differentiation line → clean auto-clear walkthrough →
blocked-then-approved walkthrough → the version-conflict "what broke" moment → metrics
→ close. Mark video recording as a human placeholder.
